# Phase 4 — GitOps Platform Bootstrap (Argo CD & Cluster Foundations)

This is the phase where your Kubernetes cluster stops being something you manually operate and starts operating itself.

From this point onward, **Git becomes the source of truth**. After the initial bootstrap, you should avoid manually applying manifests with `kubectl apply` except for emergency recovery scenarios.

---

# Goal

By the end of this phase:

* Argo CD is installed.
* The cluster bootstraps itself from Git.
* Platform components are managed declaratively.
* Applications are **not** deployed yet (OpenTelemetry Demo comes in the next phase).
* The repository supports multiple environments cleanly.

---

# Why GitOps?

Without GitOps:

```text
Developer

↓

kubectl apply

↓

Cluster
```

Problems:

* No audit trail
* Manual changes
* Configuration drift
* Hard to recover
* Difficult rollbacks

---

With GitOps:

```text
Git

↓

ArgoCD

↓

Cluster
```

Benefits:

* Git is the desired state
* Automatic reconciliation
* Rollbacks through Git history
* Drift detection
* Better collaboration

# Bootstrap Strategy

Bootstrapping should happen only once.

Terraform creates:

* GKE
* Namespace
* ArgoCD Helm Release (or manifests)

After that:

```text
Terraform

↓

Install ArgoCD

↓

ArgoCD owns everything else
```

Terraform should **not** continuously manage Kubernetes applications.

---

# Why Separate Terraform and ArgoCD?

Many beginners do this:

```text
Terraform

↓

Deploy Kubernetes Resources

↓

Deploy Helm

↓

Deploy Apps

↓

Deploy Monitoring
```

This mixes cloud infrastructure and application lifecycle.

A better separation is:

```text
Terraform

↓

Cloud Infrastructure

↓

ArgoCD

↓

Everything Inside Kubernetes
```

Terraform manages **cloud**.

Argo manages **Kubernetes**.

# Git Branch Strategy

Keep it simple:

```text

↓

production

feature/*
```

Or, if you prefer environment branches:

```text

↓

↓
```

I generally recommend using **one main branch plus environment-specific configuration directories** rather than long-lived environment branches. It keeps Git history cleaner and aligns well with GitOps.

# How this improves on the upstream OpenTelemetry Demo

The upstream OpenTelemetry Demo focuses on **deploying an application**. It assumes the Kubernetes platform already exists and leaves lifecycle management to the operator.

Our platform introduces a dedicated GitOps control plane:

* **Terraform** owns cloud infrastructure (GCP resources).
* **Argo CD** owns everything inside Kubernetes.
* The cluster continuously reconciles itself against Git.
* Multi-environment deployments are built in from the start.
* Future additions—cert-manager, External Secrets, Kyverno, Istio, OpenTelemetry Demo itself—are all added as GitOps-managed applications instead of manual installations.

This creates a clean separation of responsibilities that scales naturally as the platform grows and is much closer to how mature platform engineering teams operate.
