# Phase 3 — Production-Grade GKE Platform

This is the phase where your project stops being "Terraform on GCP" and becomes a **Kubernetes Platform**.

Most tutorials create a cluster like this:

```bash
gcloud container clusters create my-cluster
```

That's enough for learning Kubernetes.

It is **not** enough for learning Platform Engineering.

Our goal is to build something that resembles what Google, Spotify, Airbnb, or many SaaS companies would actually operate (while still keeping costs reasonable).

---

# Goal of Phase 3

By the end of this phase, we'll have:

* Production-ready GKE Cluster
* Private Cluster
* Workload Identity
* Multiple Node Pools
* Autoscaling
* Cluster Autoscaler
* GKE Dataplane V2
* Shielded Nodes
* Binary Authorization (prepared)
* Network Policies
* Logging
* Monitoring
* Gateway ready
* GitOps ready

No applications yet.

No ArgoCD yet.

No Helm yet.

Just a hardened Kubernetes platform.

# Step 1 — Private Cluster

Never create

```text
Public Nodes
```

Instead

```text
Private Nodes

↓

Private Control Plane

↓

Authorized Networks
```

Benefits

* No public node IPs
* Smaller attack surface
* Production standard
* Easier compliance

---

# Step 2 — Regional Cluster

Don't use

```text
Zonal Cluster
```

Instead

```text
Regional Cluster

asia-south1

↓

a

b

c
```

Advantages

* HA control plane
* Better availability
* Automatic resilience

---

# Step 3 — Release Channel

Instead of manually upgrading Kubernetes:

```text
Rapid

Regular

Stable
```

We'll use

```text
Regular
```

Reason

* Predictable upgrades
* New enough features
* Lower risk than Rapid

---

# Step 4 — Version Strategy

Don't pin an old Kubernetes version forever.

Instead

```text
Regular Channel

↓

Automatic Patch Upgrades

↓

Controlled Minor Upgrades
```

This reflects how managed Kubernetes is typically operated.

---

# Step 7 — Workload Identity

One of the biggest improvements over many tutorials.

Instead of:

```text
Secret

↓

JSON Key

↓

Mounted Inside Pod
```

Use

```text
Pod

↓

Kubernetes SA

↓

GCP Workload Identity

↓

Google Service Account

↓

Secret Manager
```

Advantages

* No long-lived keys
* Automatic credential rotation
* Least privilege
* Native GCP integration

Later phases (External Secrets, Cloud Storage, Artifact Registry) all rely on this.

---

# Step 8 — Dataplane V2

Enable

```text
GKE Dataplane V2
```

Benefits

* eBPF networking
* Better observability
* Better network policy performance
* Lower overhead

This is one of the strongest reasons to choose GKE over self-managed Kubernetes.

# Step 16 — Node Labels

Every node pool gets labels.

Example:

```text
workload=system

workload=general

workload=spot
```

Pods later use:

```yaml
nodeSelector:

affinity

tolerations
```

This becomes important for observability, security, and chaos workloads.

---

# Step 17 — Taints

Example

System Pool

```text
Critical Addons Only
```

Application pods cannot accidentally schedule there.

Likewise:

```text
Spot Nodes

↓

Only workloads that tolerate interruption
```

---

# Step 18 — Maintenance Windows

Configure maintenance windows.

Production clusters shouldn't upgrade randomly during peak hours.

Even for a portfolio project, documenting this shows operational thinking.

---

# Step 19 — Backup Preparation

We'll introduce Backup for GKE in a later phase, but enable the necessary APIs and document the strategy now.

This avoids surprises when disaster recovery is added.

# Step 21 — Terraform Module Layout

Enhance the `gke` module to manage:

```text
gke/

├── cluster.tf
├── nodepools.tf
├── workload_identity.tf
├── logging.tf
├── monitoring.tf
├── autoscaling.tf
├── outputs.tf
├── variables.tf
```

Keep related concerns separate rather than putting everything into one `main.tf`.

# Improvements over the upstream OpenTelemetry Demo

This is where our project starts to diverge significantly from the upstream demo:

| Upstream Demo                       | Our Platform                                                                                              |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Assumes a Kubernetes cluster exists | Provisions the entire GCP infrastructure with Terraform                                                   |
| Generic Kubernetes deployment       | Private, production-grade GKE cluster                                                                     |
| Single workload focus               | Multi-pool Kubernetes platform with workload isolation                                                    |
| No cloud IAM integration            | Workload Identity for keyless authentication                                                              |
| Basic cluster assumptions           | Hardened cluster with Dataplane V2, Shielded Nodes, Network Policies, autoscaling, and managed operations |

This foundation sets up the later phases—GitOps, security, observability, progressive delivery, and SRE—without requiring major architectural changes.
