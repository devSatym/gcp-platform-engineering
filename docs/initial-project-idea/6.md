# Phase 6 — Enterprise CI/CD & Software Supply Chain

This is where the project transforms from **GitOps** into a complete **Software Delivery Platform**.

Most GitHub repositories stop at:

```text
Push

↓

Build Docker Image

↓

Deploy
```

That is **CI/CD**.

We are building a **Software Supply Chain**.

Modern companies like Google, Spotify, Uber, and Shopify care about much more than just deploying containers.

Every deployment should answer questions like:

* Where did this image come from?
* Who built it?
* Was it scanned?
* Does it contain vulnerabilities?
* Can we trust it?
* Can we reproduce it?
* Is it signed?
* Can Kubernetes verify it?

This entire phase answers those questions.

---

# Phase Goal

Build a complete CI/CD pipeline with:

* GitHub Actions
* Artifact Registry
* Image Scanning
* SBOM
* Image Signing
* GitOps Automation
* PR Validation

* Binary Authorization preparation

# CI Architecture

We'll split GitHub Actions into multiple workflows instead of one huge YAML.

```text
.github/

workflows/

    ci.yaml

    security.yaml

    release.yaml

    terraform.yaml

    documentation.yaml

    dependency-update.yaml
```

Each workflow has a single responsibility.

---

# Why Separate Workflows?

Many repositories create:

```yaml
build.yml
```

with

500+ lines.

That's difficult to maintain.

Instead:

CI

handles code quality.

Security

handles supply-chain security.

Release

handles image publishing.

Terraform

handles infrastructure.

---

# Workflow 1 — Pull Request Validation

Runs on every PR.

Pipeline:

```text
Checkout

↓

Setup Runtime

↓

Install Dependencies

↓

Lint

↓

Unit Tests

↓

Helm Lint

↓

Terraform Validate

↓

YAML Validation

↓

Markdown Lint

↓

Success
```

No images are built yet.

Purpose:

Catch mistakes before merge.

---

# Workflow 2 — Build

Only after merge.

Pipeline:

```text
Checkout

↓

Build Docker Images

↓

Tag

↓

Upload Build Artifacts
```

Image tag strategy:

```text
Semantic Version

+

Git SHA

+

Build Number
```

Example:

```text
frontend

v1.2.3

sha-8ab912

build-102
```

Never use `latest`.

# Improvements over the upstream OpenTelemetry Demo

The upstream OpenTelemetry Demo includes GitHub Actions for building and testing, but its focus is maintaining the demo application itself.

Our platform extends that into a production-grade software supply chain:

| Upstream Demo                      | Our Platform                                                             |
| ---------------------------------- | ------------------------------------------------------------------------ |
| Build/test workflows               | End-to-end CI/CD with environment promotion                              |
| Public image publishing            | Private Artifact Registry                                                |
| Basic image builds                 | Multi-architecture Buildx builds with caching                            |
| No mandatory SBOM/signing pipeline | SBOM, vulnerability scanning, Cosign signing, provenance                 |
| Manual deployment choices          | GitOps-driven deployment updates                                         |
| Standard CI checks                 | Infrastructure validation, Helm validation, secret scanning, smoke tests |
| Application-centric                | Platform-centric with Binary Authorization and delivery observability    |

## One enhancement I'd add beyond many production examples

I would introduce **deployment verification gates based on telemetry**.

Instead of considering a deployment successful as soon as Kubernetes reports the Pods as Ready, the pipeline should also verify operational signals for a short observation window:

* HTTP success rate remains above a defined threshold.
* Error rate does not spike.
* P95 latency stays within acceptable limits.
* OpenTelemetry traces are flowing correctly.
* Key business transactions (e.g., checkout) complete successfully.

This makes deployment health dependent on **real application behavior**, not just Kubernetes readiness, and it lays the groundwork for the progressive delivery and SRE phases that follow.
