# Phase 5 — Deploy & Productionize the OpenTelemetry Demo on GKE

This is the first phase where we finally deploy the **OpenTelemetry Demo**.

But here's the important distinction:

> We are **not** deploying the demo the way the upstream project expects.
>
> We are **re-architecting it to behave like a production workload on GCP.**

The upstream project is intentionally optimized for learning observability.

We are optimizing it for:

* Platform Engineering
* Kubernetes
* Cloud Native
* GCP
* SRE
* DevOps
* AI Infrastructure

This phase is where our project begins to become unique.

# GCP Artifact Registry

The upstream project pulls images from public registries.

We'll mirror images into **Artifact Registry**.

Flow:

```
GitHub Actions

↓

Build Images

↓

Artifact Registry

↓

GKE
```

Benefits:

* Faster pulls
* Private images
* Better supply-chain control
* Easier image signing later

# Resource Requests & Limits

The upstream defaults are intentionally lightweight.

We'll tune each service.

Example philosophy:

| Service        | CPU    | Memory          |
| -------------- | ------ | --------------- |
| Frontend       | Medium | Medium          |
| Checkout       | Higher | Medium          |
| Payment        | Higher | Higher          |
| Collector      | Medium | Medium          |
| Grafana        | Medium | Medium          |
| Load Generator | Low    | Low (Spot only) |

This becomes the baseline for autoscaling in later phases.

# Scheduling Strategy

Use node labels, selectors, and tolerations.

Example:

**System Pool**

* platform components only

**General Pool**

* business microservices

**Spot Pool**

* load generator
* experimental jobs

This keeps expensive workloads off Spot nodes.

---

# Affinity Rules

Use:

* Pod Anti-Affinity
* Topology Spread Constraints

This improves resilience.

# Feature Flags

The upstream demo already uses `flagd`.

Extend this by creating environment-specific flag configurations.

Examples:

* Enable experimental recommendations only in `dev`.

# Load Generator

The upstream continuously generates traffic.

We'll improve its deployment:

* Run only in `dev` by default.
* Schedule it on Spot nodes.
* Allow configurable request rates.
* Disable it entirely in `prod` unless running controlled tests.

This reduces unnecessary cost.

# Improvements over the upstream OpenTelemetry Demo

This is where your project starts becoming a **platform engineering case study**, not just a deployment.

| Upstream Demo                | Our Platform                                                    |
| ---------------------------- | --------------------------------------------------------------- |
| Generic Helm deployment      | GCP-optimized Helm overlays with GitOps                         |
| Public container images      | Images mirrored to Artifact Registry                            |
| Demo resource sizing         | Service-specific CPU, memory, and scheduling policies           |
| Flat deployment mindset      | Tiered business, platform, and non-critical workloads           |
| Basic ingress                | Google Load Balancer + managed TLS                              |
| Single telemetry destination | Collector prepared for multiple open-source and GCP backends    |
| Load generator always active | Environment-aware, cost-optimized traffic generation            |
| Focus on observability       | Focus on production operations, resilience, and platform design |

One additional enhancement I'd strongly recommend beyond the upstream architecture is to introduce **Redis/Valkey-backed session resilience testing**. Use controlled failures (later with Chaos Mesh) to demonstrate that losing a cache node affects latency but not overall checkout correctness. That's the kind of operational scenario that turns this from a deployment exercise into a realistic platform engineering showcase.
