# Step 6 — Architecture Principles

Every future decision should follow a few guiding principles:

* **Infrastructure as Code only** — no manual console changes after initial setup.
* **GitOps-first** — Kubernetes state comes from Git.
* **Immutable deployments** — no in-place image modifications.
* **Least privilege** — IAM permissions are narrowly scoped.
* **Managed services where practical** — use GCP-managed offerings when they reduce operational burden.
* **Observability by default** — every component exposes metrics, logs, and traces.
* **Security built in** — scanning, signing, and policy enforcement are part of the delivery pipeline.

---

# Step 7 — Environment Strategy

We'll start with three environments from day one, even if they initially point to a single cluster.

```
dev

↓

stage

↓

prod
```

Each environment gets:

* separate Terraform variables,
* separate Helm values,
* separate Argo CD Applications,
* separate secrets,
* independent rollout policies.

This makes later expansion to multiple clusters much easier.

# Step 9 — Naming Standards

Define conventions now to avoid inconsistency later.

Examples:

* GKE clusters: `otel-dev-gke`, `otel-stage-gke`, `otel-prod-gke`
* Artifact Registry: `platform-images`
* Terraform state bucket: `platform-tf-state`
* Service accounts: `sa-argocd`, `sa-external-secrets`, `sa-github-actions`
* Namespaces: `platform-system`, `observability`, `security`, `applications`

Consistent naming makes automation and documentation much easier.

By the end of this phase, the repository should contain:
