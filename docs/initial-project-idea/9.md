# Why add a Service Mesh?

Without a service mesh, each application is responsible for implementing:

* Retries
* Timeouts
* TLS
* Circuit breakers
* Traffic routing
* Metrics
* Access policies

That means every team solves the same problems repeatedly.

A service mesh moves these concerns into the platform.

# Where I would improve beyond a typical Istio deployment

Rather than treating Istio as "just another component," I'd make it the **network control plane** of the platform.

Specifically:

1. **Replace the upstream Envoy frontend proxy over time.** The OpenTelemetry Demo uses an Envoy proxy as part of the application architecture. I'd evaluate whether some routing responsibilities can move into the platform's Istio Gateway while keeping the application-specific behavior intact. This reduces duplicated proxy logic and makes the platform architecture cleaner.

2. **Adopt the Kubernetes Gateway API instead of relying solely on Istio's older Gateway resources.** Gateway API is becoming the long-term Kubernetes standard and is increasingly supported across vendors.

3. **Instrument the mesh itself.** Create dedicated dashboards showing:

   * mTLS adoption (% encrypted traffic)
   * Request retries
   * Authorization denials
   * Cross-service latency
   * Sidecar resource usage
   * East-west traffic flows

This turns the service mesh into an observable, first-class platform component rather than an invisible networking layer.
