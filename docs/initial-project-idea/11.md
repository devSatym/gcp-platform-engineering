# Phase 11 — Kubernetes Autoscaling & Capacity Engineering

This is where your project starts behaving like a **living production platform** instead of a static Kubernetes deployment.

Most Kubernetes tutorials teach:

```yaml
replicas: 3
```

That's not how production works.

Real production platforms constantly answer questions like:

* How many Pods should exist right now?
* Should we add another node?
* Is CPU the bottleneck?
* Is queue length the bottleneck?
* Is latency increasing?
* Are we wasting money?
* Can we survive Black Friday traffic?

This phase is about teaching the platform to answer those questions automatically.

---

# Step 1 — Autoscaling Philosophy

There are four independent scaling layers.

```
Application

↓

Pod

↓

Node

↓

Cluster
```

Each solves a different problem.

---

# Step 2 — Horizontal Pod Autoscaler

First scaling layer.

```
CPU ↑

↓

Pods ↑
```

Example

```text
2 Pods

↓

6 Pods
```

No infrastructure changes.

Only application replicas.

---

# Step 3 — Memory-Based Scaling

CPU isn't enough.

Example

Recommendation Service

```
CPU

20%

Memory

95%
```

CPU scaling would never trigger.

Memory scaling would.

Each service needs different scaling signals.

---

# Step 4 — Custom Metrics

This is where the project becomes interesting.

Instead of scaling on CPU,

scale on business metrics.

Examples

Checkout

```
Orders / Second
```

Payment

```
Transactions / Second
```

Recommendation

```
Requests / Second
```

Cart

```
Active Sessions
```

This aligns scaling with actual workload.

---

# Step 5 — OpenTelemetry Metrics as Scaling Signals

Because the application already emits telemetry,

we can expose selected metrics to the Kubernetes Metrics API.

Examples:

* Request rate
* Queue depth
* Latency

The platform can then react to application behavior, not just resource usage.

---

# Step 6 — KEDA

This is where Kubernetes becomes event-driven.

Instead of

```
CPU ↑
```

Use

```
Kafka Lag

↓

Scale
```

or

```
Pub/Sub Messages

↓

Scale
```

or

```
Prometheus Metric

↓

Scale
```

Even if the CPU is idle.

# Step 8 — Vertical Pod Autoscaler

HPA changes the number of Pods.

VPA changes Pod size.

Example

```
Current

500Mi

↓

Recommended

900Mi
```

It helps optimize resource requests.

---

# Step 9 — Goldilocks

Introduce **Goldilocks**.

It analyzes VPA recommendations and helps right-size workloads.

Instead of guessing requests and limits, you'll have data-driven recommendations.

This also prepares you for the cost optimization phase.

---

# Step 10 — Cluster Autoscaler

Eventually HPA creates more Pods than the cluster can schedule.

```
Pods Pending

↓

Cluster Autoscaler

↓

New Node

↓

Pods Scheduled
```

This closes the scaling loop.

---

# Step 11 — Multi-Pool Scaling

Different node pools scale differently.

Example

System Pool

```
Minimum

2
```

General Pool

```
2–20
```

```

```

# Step 12 — Spot Node Strategy

The upstream load generator is ideal for Spot nodes.

Examples

Spot Pool

* Load Generator
* Batch Jobs
* Experiments
* Chaos

Never schedule

* Payment
* Checkout
* Frontend

onto Spot nodes.

---

# Step 13 — Scaling Policies

Avoid oscillation.

Instead of:

```
Scale

↓

Immediately Scale Down
```

Configure stabilization windows.

Examples:

* Slow scale down
* Faster scale up

This reduces unnecessary churn.

---

# One architectural enhancement I'd strongly recommend

Rather than treating autoscaling as a Kubernetes feature, treat it as a **capacity engineering system**.

I would create a dedicated `capacity/` section in the repository containing:

```text
capacity/
├── load-tests/
├── scaling-policies/
├── capacity-models/
├── benchmark-results/
├── k6/
├── dashboards/
└── reports/
```

For each major service (Frontend, Checkout, Payment, Collector), publish benchmark reports answering questions like:

* How many requests/sec can one Pod handle?
* At what point does latency degrade?
* What HPA thresholds performed best?
* What is the cost per additional 1,000 requests?

This kind of quantitative analysis is rare in portfolio projects and shows that you're thinking not just about **running Kubernetes**, but about **engineering reliable and efficient systems**.
