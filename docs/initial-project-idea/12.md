# Phase 12 — Chaos Engineering & Resilience Testing

This is where your project stops being **"we think it works"** and becomes **"we have evidence it survives failure."**

Almost every portfolio project demonstrates the happy path.

Production engineering is about the unhappy path.

Companies don't hire Platform Engineers because clusters work.

They hire them because clusters **continue working when things fail.**

This phase demonstrates exactly that.

---

# Why Chaos Engineering?

Imagine the Payment service crashes.

Can you answer these questions?

* Does Checkout fail?
* Does Istio retry?
* Does the HPA recover?
* Are alerts triggered?
* Does the trace show the problem?
* Does the rollout pause?
* Does the SLO burn rate increase?
* Can operators identify the root cause quickly?

If the answer is "I don't know", then you don't know whether your platform is resilient.

Chaos Engineering provides those answers.

# Step 1 — Why Chaos Mesh?

There are multiple options:

* Chaos Mesh
* LitmusChaos
* PowerfulSeal

I'd choose **Chaos Mesh** because:

* Kubernetes-native CRDs
* Rich experiment types
* Active ecosystem
* Good GitOps compatibility
* Excellent visualizations

Keep LitmusChaos as a comparison in the documentation if you want to discuss trade-offs.

# My biggest architectural recommendation

I would avoid treating Chaos Engineering as a collection of isolated experiments.

Instead, organize it around **failure scenarios that mirror real production incidents**.

For example:

```text
scenarios/
├── checkout-payment-timeout/
├── collector-overload/
├── node-loss-during-canary/
├── secret-manager-unavailable/
├── dns-resolution-failure/
├── spot-node-preemption/
└── payment-service-crash/
```

Each scenario would include:

* Architecture diagram
* Expected behavior
* Chaos experiment manifests
* Dashboards to watch
* Runbook
* Success criteria
* Sample incident report

This transforms the repository from a list of Kubernetes features into a collection of **operational playbooks**, which is much closer to how mature platform engineering and SRE teams think about system reliability.
