Excellent. Now we move to the first "real" infrastructure phase.

This phase is probably the **most important Terraform phase** in the entire project. A bad networking design forces painful refactoring later; a good one supports every subsequent capability (GKE, GitOps, observability, service mesh, etc.).

# Phase 2 — GCP Foundation & Network Architecture

## Objective

Build the cloud foundation that everything else depends on.

By the end of this phase, you'll have:

* A dedicated GCP project (or projects, if using an organization)
* Remote Terraform state
* A production-style VPC
* Private subnet architecture
* Cloud Router and Cloud NAT
* Firewall rules
* Private GKE-ready networking
* IP allocation strategy
* Reusable Terraform modules

No Kubernetes cluster yet—that comes in Phase 3.

# Step 3 — Remote Terraform State

Never store state locally for collaborative work.

We'll use:

```text
Cloud Storage Bucket

↓

Versioning

↓

Encryption

↓

State Locking (via GCS backend capabilities)
```

Recommended bucket:

```text

```

* Uniform bucket-level access
* Public access prevention
* Lifecycle rules for old versions

Future enhancements:

* Separate state buckets per environment
* Dedicated bootstrap project

# Step 4 — VPC Design

We'll use a **custom-mode VPC**, not the default network.

Reason:

* predictable IP planning
* no unnecessary subnets
* enterprise best practice

```text
VPC

platform-vpc
```

# Step 5 — Regional Design

Choose one primary region.

Example:

```text
asia-south1 (Mumbai)
```

Why?

* Lower latency for India
* Lower egress to nearby users
* Widely supported GKE features

Future expansion:

```text
asia-south1

↓

asia-southeast1

↓

us-central1
```

# Step 6 — Subnet Strategy

Separate responsibilities instead of using one flat network.

Example:

```text
VPC

│

├── gke-subnet

├── proxy-subnet

├── management-subnet

└── future-data-subnet
```

Why?

* Security
* Easier firewall management
* Better future scalability

---

# Step 7 — IP Address Planning

Don't randomly pick CIDRs.

Plan for growth.

Example:

```text
VPC

10.0.0.0/16

│

├── GKE

10.0.0.0/20

│

├── Management

10.0.16.0/24

│

├── Proxy

10.0.17.0/24

│

└── Reserved

Remaining space
```

This leaves plenty of room for future clusters or services.

---

# Step 8 — Secondary IP Ranges

GKE uses alias IPs, so allocate secondary ranges from the beginning.

Example:

```text
Pods

10.10.0.0/16

Services

10.20.0.0/20
```

Benefits:

* Cleaner networking
* Easier scaling
* Required for VPC-native GKE clusters

# Step 9 — Cloud Router

Private nodes still need outbound internet access for:

* pulling container images
* package updates
* external APIs
* GitHub Actions webhooks (if applicable)

Traffic flow:

```text
Private Nodes

↓

Cloud Router

↓

Cloud NAT

↓

Internet
```

Cloud Router manages dynamic routes for Cloud NAT.

---

# Step 10 — Cloud NAT

**Do not assign public IPs to GKE nodes.**

Instead:

```text
Private Nodes

↓

Cloud NAT

↓

Internet
```

Advantages:

* Better security
* Lower attack surface
* Production best practice

---

# Step 11 — Firewall Rules

Design with least privilege.

Examples:

### Internal communication

Allow:

* node ↔ node
* pod ↔ pod
* control plane ↔ nodes

### SSH

Avoid opening SSH entirely if possible.

Prefer:

* Identity-Aware Proxy (IAP)
* `kubectl exec`
* Cloud Shell

### Health checks

Allow only Google health check ranges where needed.

---

# Step 12 — Private Google Access

Enable Private Google Access on subnets.

This lets private resources reach Google APIs without public IPs.

Examples:

* Artifact Registry
* Secret Manager
* Cloud Storage

# Step 14 — Service Accounts

Avoid using the default Compute Engine service account.

Create dedicated service accounts for:

* Terraform
* GKE nodes
* Argo CD
* External Secrets
* GitHub Actions (via Workload Identity Federation)

Grant only the permissions each component needs.

## Design improvement over a typical demo

One optimization I'd make for this project is to **use a private GKE cluster from the beginning** rather than starting with a public cluster and hardening it later. That decision influences the networking, IAM, GitHub Actions authentication, and GitOps setup, but it more closely reflects how many production GKE environments are built today. It also makes the later phases on security and platform engineering feel like a natural continuation rather than retrofits.
