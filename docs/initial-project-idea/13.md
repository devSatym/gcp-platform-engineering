# Phase 13 — Site Reliability Engineering (SRE), Operations & Incident Management

This is the phase where your repository stops looking like a DevOps project and starts looking like an **operations platform**.

Most people build infrastructure.

Very few demonstrate **how they operate it.**

This phase answers questions like:

* How do we know users are happy?
* What defines an outage?
* Who gets alerted?
* How do we investigate?
* How do we recover?
* How do we learn from failures?

This is the phase that many senior interviews focus on.

---

# Step 3 — Define SLOs

Example:

Frontend

| Metric       | Target   |
| ------------ | -------- |
| Availability | 99.95%   |
| P95 Latency  | < 300 ms |
| Error Rate   | < 0.5%   |

Checkout

| Metric           | Target |
| ---------------- | ------ |
| Availability     | 99.9%  |
| Checkout Success | > 99%  |

Payment

| Metric       | Target   |
| ------------ | -------- |
| Success Rate | > 99.95% |
| Latency      | < 400 ms |

These are platform objectives, not Kubernetes objectives.

---

# Step 4 — Error Budgets

One of the most important SRE concepts.

Example

99.9%

means

approximately

43 minutes

of downtime per month.

Instead of saying

"We had downtime"

we can say

"We consumed 20% of the monthly error budget."

That's a much more useful operational metric.

---

# Step 5 — Burn Rate Alerts

Don't alert on every failure.

Alert when the error budget is being consumed too quickly.

Example

Normal

```text
0.1%

Error Rate
```

↓

No Alert

Sudden Spike

```text
8%

Errors

↓

Burn Rate

↓

Critical Alert
```

This dramatically reduces alert fatigue.

---

# Step 8 — Alert Quality

Every alert should answer:

* What failed?
* Why does it matter?
* Which dashboards should I open?
* Which runbook should I follow?
* Which services are affected?

Avoid alerts like:

```text
CPU High
```

Prefer:

> Payment latency exceeded the SLO for 15 minutes. Open Dashboard X and Runbook Y.

---

# The biggest enhancement I'd make

This is where I think you can build something that very few public repositories have.

Create a dedicated **Operations Center** inside the repository:

```text
operations/
├── slos/
├── alerts/
├── runbooks/
├── postmortems/
├── reliability-reports/
├── incident-timelines/
├── executive-dashboards/
└── ai-copilot/
```

Each incident should have a complete operational record:

* The chaos experiment or real trigger.
* Grafana dashboard snapshots.
* Relevant logs and traces.
* The alert that fired.
* The runbook followed.
* The recovery timeline.
* The postmortem.
* The AI-generated incident summary.

This turns the repository into far more than a Kubernetes demo—it becomes a complete record of how a production platform is operated, which is exactly the perspective expected from senior Platform Engineers and SREs.
