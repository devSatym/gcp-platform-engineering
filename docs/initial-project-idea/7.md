# Phase 7 — Enterprise Security Platform (Cloud + Kubernetes + Supply Chain)

This is where the project changes from being a **DevOps project** into a **Platform Security Engineering project**.

Most portfolio projects stop after:

```text
Docker

↓

Kubernetes

↓

CI/CD
```

Very few engineers build the security layer.

This phase is arguably the biggest differentiator on your resume.

---

# Phase Goal

Build a **Defense in Depth** security architecture.

Instead of relying on one security tool, we'll secure every layer.

```text
Developer

↓

GitHub

↓

CI/CD

↓

Container

↓

Artifact Registry

↓

GKE

↓

Kubernetes

↓

Application

↓

Runtime
```

Every layer has protection.

# Security Architecture

We'll think in terms of layers.

```text
Cloud Security

↓

Identity

↓

Supply Chain

↓

Kubernetes

↓

Network

↓

Secrets

↓

Runtime

↓

Application
```

Every future decision should strengthen one of these layers.

---

# Layer 1 — Cloud IAM

Never use overly broad permissions.

Instead of:

```text
Editor
```

Create dedicated service accounts for:

* Terraform
* GitHub Actions
* Argo CD
* External Secrets
* Monitoring
* Backup
* GKE nodes

Grant only the permissions each component needs.

Example:

```text
GitHub Actions

↓

Artifact Registry Writer

Secret Manager Access (if required)

Nothing Else
```

---

# Layer 2 — Workload Identity Everywhere

By now, every workload accessing GCP services should use **Workload Identity**.

No JSON keys.

No mounted credentials.

Example:

```text
Pod

↓

Kubernetes Service Account

↓

Workload Identity

↓

Google Service Account

↓

Secret Manager
```

This eliminates an entire class of credential management problems.

---

# Layer 3 — Secret Management

Remove secrets from Git.

Architecture:

```text
Git

↓

External Secrets Operator

↓

Secret Manager

↓

Pod
```

Secrets never live in:

* Helm values
* ConfigMaps
* Kubernetes manifests
* GitHub repository

Future enhancements could include secret rotation policies and audit logging.

---

# Layer 4 — Kubernetes Admission Control

Install **Kyverno** (or OPA Gatekeeper, but I'd choose Kyverno for this project because of its approachable policy syntax and strong Kubernetes integration).

Policies to enforce:

* No `latest` image tags
* Images must come from Artifact Registry
* Resource requests and limits required
* Liveness and readiness probes required
* Containers must run as non-root
* Privileged containers denied
* HostPath volumes denied
* Host networking denied
* Read-only root filesystem required where practical

Now the cluster actively prevents insecure deployments.

---

# Layer 5 — Pod Security Standards

Adopt the Kubernetes Pod Security Standards.

Namespaces can have different enforcement levels.

Example philosophy:

```text
platform-system

Restricted

applications

Restricted

observability

Baseline (if specific components require it)
```

Document any exceptions instead of silently allowing them.

---

# Layer 6 — Network Security

Enable **default deny** NetworkPolicies.

Communication becomes explicit rather than implicit.

Example:

```text
Frontend

↓

Checkout

↓

Payment
```

Allowed.

But:

```text
Frontend

×

OpenSearch
```

Denied.

Design policies around application flows rather than broad namespace access.

---

# Layer 7 — Container Hardening

Review each image.

Prefer:

* Distroless images
* Minimal base images
* Non-root users
* Read-only filesystem
* Dropped Linux capabilities

Track progress in documentation so readers can see which services have been hardened.

---

# Layer 8 — Runtime Security

Introduce **Falco**.

Detect events such as:

* Unexpected shell execution
* Privilege escalation
* Writes to sensitive directories
* Suspicious network activity

Flow:

```text
Container

↓

Falco

↓

Alert
```

This complements preventive controls with runtime detection.

---

# Layer 9 — Supply Chain Enforcement

Extend Phase 6.

Pipeline becomes:

```text
Build

↓

SBOM

↓

Scan

↓

Sign

↓

Artifact Registry

↓

Binary Authorization

↓

Deploy
```

Unsigned or policy-violating images are rejected before reaching GKE.

---

# Layer 10 — Image Policy

Allow deployments only from trusted registries.

Example:

```text
Artifact Registry

↓

Allowed
```

```text
docker.io/random-user

↓

Denied
```

This prevents accidental use of untrusted images.

---

# Layer 11 — Infrastructure Security Scanning

Before applying Terraform:

Run tools such as:

* Checkov
* tfsec (if desired)
* TFLint

These catch insecure infrastructure configurations early.

---

# Layer 12 — Kubernetes Manifest Scanning

Scan manifests and Helm charts for security issues before they reach the cluster.

Examples include:

* Missing security contexts
* Privileged containers
* Dangerous capabilities
* Excessive RBAC permissions

---

# Layer 13 — RBAC Review

Avoid granting `cluster-admin` broadly.

Create roles such as:

* Platform Admin
* Application Developer
* Read-Only Observer
* Security Auditor

Apply least privilege consistently.

---

# Layer 14 — Namespace Isolation

Separate workloads into namespaces with clear boundaries.

Example:

```text
argocd

platform-system

observability

security

applications
```

Each namespace gets:

* ResourceQuota
* LimitRange
* NetworkPolicy
* Pod Security level

---

# Layer 15 — Encryption

Ensure encryption:

* At rest (GCP-managed by default where applicable)
* In transit (TLS)
* Between services (prepare for Istio mTLS in a later phase)

Document where encryption is provided by GCP versus Kubernetes.

---

# Layer 16 — Audit Logging

Enable and retain:

* Kubernetes audit logs
* GKE audit logs
* IAM audit logs
* Secret Manager audit logs

These become valuable during incident investigations.

---

# Layer 17 — Security Monitoring

Create dashboards for:

* Admission policy violations
* Falco alerts
* Authentication failures
* Binary Authorization denials
* Secret access patterns

Security should be observable, not just configured.

---

# Layer 18 — Compliance Mapping

Map implemented controls to common frameworks at a high level.

Examples:

* CIS Kubernetes Benchmark
* NIST Cybersecurity Framework
* SOC 2 principles

You don't need formal compliance, but showing awareness is valuable.

---

# Layer 19 — Threat Modeling

Document a simple threat model.

Examples:

| Threat                      | Mitigation                         |
| --------------------------- | ---------------------------------- |
| Compromised container image | Cosign + Binary Authorization      |
| Leaked credentials          | Workload Identity + Secret Manager |
| Lateral movement            | NetworkPolicies                    |
| Privilege escalation        | Pod Security + Kyverno             |
| Malicious runtime behavior  | Falco                              |

This demonstrates security thinking beyond tooling.

---

# Layer 20 — Security Testing

Add repeatable tests.

Examples:

* Attempt to deploy a `latest` tag (should fail)
* Attempt to deploy a privileged Pod (should fail)
* Attempt to use an unauthorized registry (should fail)
* Attempt to access Secret Manager without permission (should fail)

These become excellent demonstrations in your documentation.

# Improvements over the upstream OpenTelemetry Demo

The upstream project demonstrates observability, not platform security. Our platform adds a comprehensive security layer around the application.

| Upstream Demo                  | Our Platform                                                         |
| ------------------------------ | -------------------------------------------------------------------- |
| Demo-focused deployment        | Defense-in-depth platform architecture                               |
| Standard Kubernetes deployment | Hardened GKE with enforced security policies                         |
| No admission policy framework  | Kyverno enforcing deployment standards                               |
| Generic secret handling        | Secret Manager + External Secrets + Workload Identity                |
| No runtime threat detection    | Falco runtime monitoring                                             |
| Supply-chain examples          | End-to-end trusted software supply chain with Binary Authorization   |
| Limited security documentation | Threat model, compliance mapping, and repeatable security validation |

## One improvement I'd make beyond this phase

I would create a **Security Validation Lab** inside the repository.

Instead of only documenting the controls, include intentionally insecure example manifests in a separate `labs/security/` directory. Each example demonstrates a specific policy failure:

* Deploying a privileged Pod.
* Using an image from an unauthorized registry.
* Omitting resource limits.
* Running as root.
* Using the `latest` tag.

The README would then show the expected Kyverno rejection or Binary Authorization failure. This turns the repository into both a production platform **and** a hands-on learning resource, making it much more compelling for reviewers and interviewers.
