# Applications Layer — `gitops/applications/`

> **Watched by:** `otel-demo-dev` Application (generated by `applications-appset.yaml`)  
> **Path:** `gitops/applications/opentelemetry-demo/values/`  
> **ArgoCD Project:** `applications`  
> **Pattern:** Multi-source (upstream chart + monorepo values overlay)

---

## Directory Structure

```
gitops/applications/
└── opentelemetry-demo/
    ├── README.md
    └── values/
        ├── base.yaml     ← Common config for ALL environments
        ├── dev.yaml      ← Dev-specific overrides (layered on top of base)
        ├── stage.yaml    ← Stage overrides
        └── prod.yaml     ← Prod overrides (higher replicas, more resources)
```

---

## How Multi-Source Values Work

The `applications-appset.yaml` specifies:

```yaml
helm:
  valueFiles:
    - $values/gitops/applications/opentelemetry-demo/values/base.yaml
    - $values/gitops/applications/opentelemetry-demo/values/{{env}}.yaml
```

Helm merges values in order — **later files override earlier ones**:
1. Upstream chart `values.yaml` (default chart values)
2. `base.yaml` (our common overrides)
3. `dev.yaml` / `stage.yaml` / `prod.yaml` (environment-specific overrides)

## `base.yaml` — Common Configuration (All Environments)

### Purpose

Applied to every environment. Contains environment-agnostic overrides.

### Key Sections

#### Default Environment Variables (All Components)

```yaml
default:
  env:
    - name: OTEL_SERVICE_NAME
      valueFrom:
        fieldRef:
          fieldPath: metadata.labels['app.kubernetes.io/component']
    - name: OTEL_RESOURCE_ATTRIBUTES
      value: "deployment.environment=$(DEPLOYMENT_ENV),k8s.cluster.name=$(CLUSTER_NAME)"
```

Injects OTel resource attributes into every pod so traces include service name, environment, and cluster.

#### Component Enablement

```yaml
components:
  image-provider:
    enabled: true    # nginx serving product images — without it, blank images on storefront
  llm:
    enabled: false   # Requires GPU/API key — skip
  product-reviews:
    enabled: false   # Requires PostgreSQL — skip until Phase 8
  postgresql:
    enabled: true    # product-catalog requires it in v0.40.9+
  product-catalog:
    enabled: true
```

Observability sub-charts disabled at base level:
```yaml
opentelemetry-collector:
  enabled: false
prometheus:
  enabled: false
grafana:
  enabled: false
jaeger:
  enabled: false
opensearch:
  enabled: false
```

**Why disabled:** These sub-charts install cluster-scoped ClusterRoles with **fixed names**. On a single cluster, enabling them for multiple environments causes `SharedResourceWarning` — ArgoCD marks apps as `Degraded`. Phase 8 will move them to dedicated ArgoCD Applications.

#### Service Tier Classification and Node Scheduling

All services are assigned to node pools via `schedulingRules.nodeSelector`:

| Tier | Services | Node Pool | Rationale |
|------|---------|-----------|-----------|
| 1 — Critical | frontend, frontend-proxy, cart, checkout, payment, product-catalog | `general` | Revenue-critical — must not be evicted |
| 2 — Supporting | email, recommendation, currency, shipping, ad, accounting, fraud-detection, quote | `general` | Support services — can tolerate brief disruption |
| 3 — Platform | flagd | `general` | Feature flags service |
| 4 — Non-critical | load-generator | **`spot`** | Interruptible — uses spot pool with taint toleration |
| Data stores | valkey-cart, kafka | `general` | Stateful — must not run on spot |

**Load generator scheduling** (spot pool requires both toleration AND nodeSelector):
```yaml
load-generator:
  schedulingRules:
    nodeSelector:
      workload: spot
    tolerations:
      - key: "workload"
        operator: "Equal"
        value: "spot"
        effect: "NoSchedule"
```

#### Resource Requests/Limits per Service

Each service has tuned requests/limits. Examples:

| Service | CPU Request | CPU Limit | RAM Request | RAM Limit | Note |
|---------|------------|-----------|------------|-----------|------|
| frontend | 100m | 500m | 128Mi | 512Mi | — |
| frontend-proxy | 50m | 200m | 64Mi | 256Mi | Envoy proxy |
| ad | 100m | 500m | 256Mi | 512Mi | JVM (Java) — needs more RAM |
| fraud-detection | 50m | 200m | 128Mi | 384Mi | Kotlin (JVM) |
| kafka | 100m | 500m | 256Mi | 512Mi | Message queue |
| load-generator | 50m | 200m | 64Mi | 256Mi | Spot node |

**JVM services** (`ad`, `fraud-detection`) get higher memory limits due to JVM heap overhead.

## `dev.yaml` — Dev Environment Overrides

Layers on top of `base.yaml`. Key dev-specific settings:

- **Replicas:** `1` for all services (base is environment-agnostic; dev sets minimum)
- **Observability sub-charts:** Optionally enabled for dev-only debugging (if single env)
- **Resource limits:** May be tighter than prod to stay within dev node capacity
- **Feature flags:** Dev-specific flagd configuration

---

## `stage.yaml` — Stage Environment Overrides

- **Replicas:** Between dev and prod (e.g., 2 for critical services)
- **Observability:** Enabled if stage has a dedicated cluster
- **Resources:** Closer to prod sizing

---

## `prod.yaml` — Production Overrides

- **Replicas:** Higher (2–3 for critical services, HPA enabled)
- **Resources:** Higher limits to handle real traffic
- **Observability:** Enabled with production-grade retention

## Key Design Decisions

### Why Not Modify the Upstream Chart?

Forking the upstream chart creates a maintenance burden — every new OTel Demo release requires manual merging. The multi-source values overlay approach lets us:
1. **Pin to a specific chart version** in the ApplicationSet `chartVersion` field
2. **Only override what we need** in our values files
3. **Update chart versions** with a single line change in `applications-appset.yaml`

### Why `kibab-case` Component Names?

```yaml
# CORRECT (chart schema requires this):
frontend-proxy:
  enabled: true

# WRONG (will be silently ignored):
frontendProxy:
  enabled: true
```

The OTel Demo chart v0.40.9+ enforces `kebab-case` in its `values.schema.json`. Using `camelCase` causes the override to be silently ignored.

### Why `priorityClassName` Is Not Set Here

PriorityClass assignment is **not supported** by the OTel Demo chart's component schema. Instead:
- `gitops/platform/priority-classes.yaml` creates the PriorityClass resources
- `business-standard` is set as `globalDefault: true` — applies to all pods without an explicit `priorityClassName`
- Pods inherit the default automatically
